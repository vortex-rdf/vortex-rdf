## [0.14.0](https://github.com/vortex-rdf/vortex-rdf/compare/v0.13.1...v0.14.0) - 2026-11-02

### Added

- Java bindings ([#103](https://github.com/vortex-rdf/vortex-rdf/pull/103)): the `org.vortexrdf` API (Java 17 or later) over a JNI library, `libvortex_rdf_jni` (the `vortex-rdf-java` crate), which opens a `.vortex` file read-only, memory-mapped (`VortexRdfStore.open(path)`) or loaded whole (`open(path, true)`), and queries it in place. By terms, on every layout: `size`, `layout`, `indexes`, `count(s, p, o, g)`, `quads(s, p, o, g)`, a `List<String[]>` of N-Triples spellings (`null` a free position, `""` the default graph), and `iterateQuads(s, p, o, g[, batchRows])`, a `QuadIterator` (and its `stream()`) that reads the match 65,536 rows at a time by default. Terms cross JNI in packed chunks, each distinct term of a chunk once, so the rows of a chunk that hold the same term share one `String`; `decodeMany` reads its codes the same way. By codes, on a Dictionary-layout store: `dictionary()` gives a `TermDictionary` (`encode`, which answers `VortexRdfStore.NONE` for a term the store lacks, `decode`, `decodeMany`, and `ranges()`, the term kinds' `CodeRange`s and the default graph's code); `countCodes`; `matchCodes`, which writes a window of `(s, p, o, g)` codes into a reusable writable direct `ByteBuffer`, `ROW_BYTES` a row; and `matchCodeChunks`, a `CodeChunks` that writes a whole match into such a buffer a chunk at a time. A code lookup is one located run where the file can locate the pattern and the general match otherwise. Streams and one-shot reads return base row order, or a `secondary-by-copy` index's order on a pattern it serves. A native error raises the unchecked `VortexException` (a malformed term names its position, `pattern subject: …`); a store may be queried from any number of threads, `close()` waits for the calls in progress and ends the store's iterators, later calls raise `IllegalStateException`, and an iterator left unclosed is freed by a cleaner. The library is loaded from the `vortexrdf.library` system property, the `VORTEX_RDF_JNI_LIB` variable, the jar's own copy for its platform (unpacked into a private directory under `java.io.tmpdir`) or `java.library.path`, in that order. ### Changed

- **Breaking:** every read of a view a `secondary-by-copy` index serves follows that index's order, as `quads()` already did, and the view's windows, keeps and partitions, and a pattern chained on one of them, stay served and follow it too. Only a view `index:posg` serves with the object unbound reads differently from base `(s, p, o, g)` order: a `?p??` match, and on file a `?p?g` one, comes in `(o, s, g)` order. Such a view read in base order in v0.13.1, and reads in the index's order now, in `row_chunks` and `code_chunks` (Python's `match_code_chunks`, JS's `matchCodeChunks`); in the N-Triples/N-Quads export (the CLI's default for `match`); in the one-shot code read `code_columns_gathered` (Python's `match_codes`, JS's `matchCodes`) of an in-memory run of more than 256 rows or a file run of at most 256, which v0.13.1 read in base order while it read every other run in the index's; and in `window`, `partitions`, `keep` and `keep_many` and a pattern chained on their views, so a window that cuts rows (Python's and JS's `limit` and `offset`) takes other rows than in v0.13.1. These narrowings count and read without sorting the run's row ids, where v0.13.1 read and sorted them all first: on file a window reads only its rows of the index child's rid column, on first need; a keep tests the column over the run in the index's order and keeps the rows it admits; and a file run the child cannot locate (a string layout's, or one a residual term filters) is read once by row index at its first narrowing. `view_statistics().sort_order` names the order every read follows: `Posg` for such a view and its narrowings, where it reported `Spog`, the order of the chunk streams. Migration: where base order matters, sort the rows by `(s, p, o, g)` (Dictionary codes sort as their terms do) before cutting a window, or build the store with the `secondary-by-reference` index or none, whose views read base order (core, python, js, cli) ([`1dd8642`](https://github.com/vortex-rdf/vortex-rdf/commit/1dd8642709eaa6eca9a03e7fa653b25847cbe495), [`8604961`](https://github.com/vortex-rdf/vortex-rdf/commit/86049617457ec4dd521a5143791318b862c50c3a), [`9e606a9`](https://github.com/vortex-rdf/vortex-rdf/commit/9e606a9580345df66e8244663143c6b98457b8d1), [`944a7be`](https://github.com/vortex-rdf/vortex-rdf/commit/944a7bec4089306cb6a493aeca826d4695a1fe43), [`fd8cdd2`](https://github.com/vortex-rdf/vortex-rdf/commit/fd8cdd2af88738e72a0efe9c0e86c97a27c38251), [`876a836`](https://github.com/vortex-rdf/vortex-rdf/commit/876a83615e43837519515120fcdca34023674938), [`4b74dce`](https://github.com/vortex-rdf/vortex-rdf/commit/4b74dce8937acb0817f5996667cdbd03363b0b7a), [`8a62be2`](https://github.com/vortex-rdf/vortex-rdf/commit/8a62be256a0625ddad8f50545eeb074bfe498c5d), [`b96b85d`](https://github.com/vortex-rdf/vortex-rdf/commit/b96b85dfdc856e50b9bfc6b41837f894a5f7109f), [`9a56901`](https://github.com/vortex-rdf/vortex-rdf/commit/9a56901a7a627e80ec20bdc28fc849e3ee6a8937) by @claude)
- **Breaking (Rust):** vortex-rdf-core and vortex-rdf-encoded-search build against Vortex 0.90, where they built against 0.88, and their public API carries Vortex types: core's `vortex_session()` (`VortexSession`), `BuiltArray::array`, `RowChunkStream` and `decode_row_chunk` (`ArrayRef`), the code buffers of `CodeChunkStream`, `code_columns_gathered`, `LocatedCodes`, `match_code_pattern`, `Keep::Set` and the `columns` kernels (`vortex_buffer::Buffer`), `from_bytes_owned` (`ByteBuffer`), `io::quads_stream_to_vortex_writer` (`VortexWrite`) and `VortexRdfError::Vortex` (`VortexError`); encoded-search's `SortedProbe::resolve`, `OwnedSortedProbe`, `ColumnChunks`, `flat_leaves` and `fetch_flat`. encoded-search depends on `vortex-layout` without its `layout` feature too, since Vortex moved its `Shared` array there, and its probes decline bit-packing with a width per 1,024-value block (`fastlanes.bitpacked.v2`), which a BtrBlocks compressor whose builder allows that form (as `empty()` does) now writes where the blocks' widths differ; store files never hold it. The store format is unchanged (`vortex-rdf.store.v2`, the same dictionary and index versions, the same frozen `CORE_2026_08_3` write edition), so stores written by 0.13.x open as before. At 262,144 quads Default and TypedObject files come out 2.5–5.4% larger (Vortex now sizes string blocks by the bytes their rows reference, so the object column's leaves hold 16,384 rows instead of 8,192) and Dictionary files keep their size. Across the core benches the upgrade alone is about 5% faster at 262,144 quads and 2.5% at 32,768: `from_bytes` opens about 30% faster, cold matches over a store opened from bytes about 24%, and file-backed code scans, chained views and a code-range `keep` 8–16%. - A file view's filter evaluation, which every read of a filtered match on a file store without an index runs, tests fewer rows. Its split tasks test the filter's code equalities, and prune by the zone maps, in order of observed selectivity (subject, object, predicate, graph until each has been tested once), where every split tested them in the pattern's `s`, `p`, `o`, `g` order, so a predicate-and-object lookup no longer reads the predicate column over a split the object rules out: the 50-row `rdf:type` lookup on the 3.5M-row BSBM file store takes 1.66 ms where it took 2.92 ms. `exists`, `size_capped` and `window` (Python `count_quads` and `match_codes` with a `limit`), which stop at their cap, evaluate a cap below one zone's 8,192 rows from the first zone, then in pieces four times the one before, where they evaluated the first split whole: `exists` takes 24.1 µs where it took 69.2 µs at 1,048,576 quads, and a cap one zone cannot reach (a probing `limit=65537`) evaluates whole splits as before. A window of a view whose earlier window kept the filter's masks cuts those masks, where it evaluated the filter again split by split (core) ([`3c67cb2`](https://github.com/vortex-rdf/vortex-rdf/commit/3c67cb2d7ade3d90ec3c42e88b290f23400176b4), [`7c4e2b5`](https://github.com/vortex-rdf/vortex-rdf/commit/7c4e2b5e98479bd3d1077654c52f054ef16b475c), [`1e67c62`](https://github.com/vortex-rdf/vortex-rdf/commit/1e67c62ac9470512f63c9013a08c59b9c19a4133) by @julianrojas87 and @claude)
- A filtered file view's uncapped count (`size()`, `count_probe` without a limit; Python `count_quads` without a `limit`), a delete's search for the rows it tombstones (`delete_matching`, `delete_quad`) and a `keep`'s pass over a file column spawn their splits onto the current tokio runtime's workers from two splits up, four per unit of available parallelism in flight, where the count and the delete polled every split on the calling task. ## [0.1.0](https://github.com/vortex-rdf/vortex-rdf/releases/tag/v0.1.0) - 2026-07-21

Initial release ([79 commits](https://github.com/vortex-rdf/vortex-rdf/commits/v0.1.0) by @julianrojas87). The entries below summarise features built across
many commits, so they are not attributed individually.

### Added

- `vortex-rdf-core`: a columnar RDF quad store built on [Vortex](https://docs.vortex.dev),
  with serialization to/from `.vortex` files and Vortex IPC streams.
- Three column layouts — `Default`, `TypedObject`, and `Dictionary` — trading off
  compression strategy and query characteristics.
- Two secondary index types — `SecondaryByReference` and `SecondaryByCopy` — for
  accelerating pattern matching beyond the primary sort order.
- Three ingestion builders — `UnsortedStream`, `SortedInMemory`, and `SortedStream`
  (out-of-core, spill-to-disk) — for building a store from a quad stream.
- `VortexRdfStore` query API: pattern matching, mutation (add/delete), and
  compaction, with row selections composing over both in-memory and file-backed
  stores.
- `vortex-rdf-cli`: a command-line interface for converting between RDF formats
  and Vortex-RDF, and for querying `.vortex` files.
- `vortex-rdf` (npm): WebAssembly bindings exposing a `VortexStore` with an
  RDF-JS-compatible `DatasetCore` interface.
