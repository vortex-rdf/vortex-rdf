One cargo bench run of core/benches/benchmark.rs — a star (one-factor-at-a-time) design over four axes: builder strategy, column layout, secondary index, and source. Each panel below isolates one axis against a fixed baseline; the raw table at the bottom holds every measured configuration.

WRITE

Serialize — ingest & encode

Building a Vortex array from 100,000 generated quads and writing it out. Baseline: default layout, no secondary index.

QUERY

Match — pattern resolution

Resolving match_pattern and materializing the matching quads, across the six routing shapes the resolver branches on: S (primary binary search, 1 row), P/O (single-column index probe, 1–2k rows), PO (two-column prefix probe, 1k rows), G (no index covers graph — mask scan, 10k rows), and SPOG (every component bound, 1 row).

DECODE

Load & decode — read-back

Opening a store and decoding every quad back out (full scan), independent of any match pattern.

DICT

Dictionary — residency

The Dictionary layout's term dictionary rides inside the quads file as an embedded metadata-segment blob (one self-contained file; the quad columns stay bare). Residency: the blob is lifted into memory at open (resident) or left in the file and reached by pruned scans through a bounded reader (file-backed) — decided by the blob's byte size. The table below shows which phase — open, cold probe, decode — the residency choice moves the cost into.

One npm run bench run of js/bench/compare.bench.ts — the VortexRdfStore WASM bindings compared against rdf-stores.js and oxigraph, on a synthetic dataset whose distinct term count scales with the rows (each subject described by about ten triples, a small closed predicate vocabulary, a mix of IRI and literal objects), across four phases: ingest, query, add, delete. Wall-clock (tinybench) — deliberately not uploaded to CodSpeed.

Term cardinality matters because it is what exercises each library's dictionary and string handling; selectivity follows the data, so each pattern's matched-row count is recorded in config.matchedRows alongside its timing.

INGEST

Bulk build

Building a store from the generated triples via each library's idiomatic bulk path (Vortex fromQuads, oxigraph new Store(quads), rdf-stores per-quad addQuad). Apples-to-oranges by construction — read it as “time to a queryable store”.

QUERY

Match — cross-library

Resolving match and counting results across routing shapes: S/P/O/PO/SPO/full on triples, G/SPOG on named graphs. Vortex quads are lazy/zero-copy, so counting doesn't materialize term strings — the full scan in particular flatters Vortex against the eager stores.

MUTATE

Add & delete

Incremental per-quad additions and deletions of a fixed batch. Vortex routes these through its tail/tombstone model, so per-quad addQuad trails the recommended addQuads batch path — both are shown.

VARIANTS

Vortex config variants

The same star design as the Rust tab, over the axes reachable from JS: column layout (Default / Dictionary) and secondary index (none / ByReference / ByCopy).

MEMORY

Peak memory (RSS)

Each adapter's full lifecycle (build, query, ingest — or add/delete for the mutation phase) runs in its own process, so this is a clean, uncontaminated peak resident-set size per adapter: the kernel-tracked high-water mark (VmHWM), not a point-in-time sample. Lower is better.

One python/bench/run.py run — the vortex_rdf bindings compared against pyoxigraph, pycottas, rdflib, and lightrdf, on the same generated dataset the JavaScript tab uses (identical moduli, identical term spellings), so rows on the two tabs describe the same data.

The shape of this comparison differs from the JavaScript one, because the libraries do. Every one of them ingests from a file, so the workload is file → store → query rather than array → store → query, and Open is a first-class column: for a file-backed format it is opening the artifact, while an in-memory store must re-parse the source on every process start. Two libraries are read-only and one is not a store at all — those cells read unsupported, which records an absent API, not a slow result.

Vortex appears once per build configuration rather than as a single row, because its knobs — column layout, secondary index, and whether the store is read from the file or loaded up front — move these numbers as much as the choice of library does. Residency is crossed with the secondary index, so each (file, memory) pair shares a build: the difference between the two is residency alone, and it can be read with an index and without one. The in-memory indexed rows are the configurations that match how pyoxigraph and rdflib hold their data.

BUILD

Build & open

Build is each library's idiomatic path from an N-Triples file to a queryable store (serialize_rdf, bulk_load, rdf2cottas, Graph.parse). Open is what a fresh process pays to query an already-built artifact: a file-backed format opens it, while pyoxigraph and rdflib hold their store in memory and must parse the source again — which is the comparison, not a flaw. lightrdf builds nothing; its “build” is one full parse, the same pass every other library must do before it can index anything.

QUERY

Match by pattern

Resolving each pattern and counting results: S/P/O/PO/SPO/full on triples, G/SPOG on named graphs. Counting is the only unit all five share, and each library materializes its own natural result form — Vortex builds N-Triples strings in Rust, pyoxigraph and rdflib yield term objects, pycottas and lightrdf yield tuples of strings. Residency differs too: the Vortex (file) rows and pycottas read from disk per query, while the Vortex (memory) rows, pyoxigraph and rdflib answer from memory. lightrdf is the no-index baseline: it has no store, so every pattern re-parses the whole source file and costs about the same regardless of selectivity.

MUTATE

Add & delete

Per-quad addition and deletion of a fixed batch. Only two of the five libraries can do this at all: the Vortex Python bindings expose no mutation API (unlike the JS bindings, which have addQuad/addQuads), pycottas's store raises “The COTTAS store is read only!”, and lightrdf is a parser with no store to mutate. Hover an unsupported cell for the reason.

FOOTPRINT

Peak memory & on-disk size

Each adapter runs in its own process and its own virtualenv, so peak RSS is the kernel-tracked high-water mark (VmHWM) for one library alone. On-disk size is the artifact the build produced; it is — for a library that keeps its store in memory and writes no file of its own, and for lightrdf it is the source N-Triples file it re-reads. Lower is better in both tables.
